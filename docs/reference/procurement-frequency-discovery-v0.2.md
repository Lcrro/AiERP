# 实际采购清单物料族发现 v0.2

## 目的与边界

v0.2 是在 v0.1 结果上的第二轮只读分析。它的目标是更可靠地发现“同一物料族的别名、规格变体和采购频次”，为后续网页审阅和多属性整合排序提供证据。

它仍然不是物料主数据发布、SKU 合并或 ERPNext 写入任务：

```text
原始采购行
→ 规范化名称、单位和可识别属性
→ 显式规则与词法候选分层
→ 分离原始名称、疑似别名、规格变体和采购事件
→ 标记单位冲突、服务/笼统行和可能误合并项
→ 输出优先级及人工复核候选
```

## 相比 v0.1 的改动

### 1. 四个维度不再混用

- `raw_name_count`：聚类中出现的不同原始名称数量；
- `alias_candidate_group_count`：同一规格键下、需要确认是否为别名的原始名称组；
- `variant_count`：同一物料族中不同物理规格键数量；
- `distinct_event_count_approx`：按 `采购日期 + 工序 + 规格键` 去重的近似采购事件数。

品牌和包装会保留在 `attributes_observed`、原始行和别名证据中，但不进入 `variant_key`。因此“公元 PPRΦ110 管”和“PPR110 管”不会仅因品牌或写法不同而被误算成两个规格；包装差异也不会单独制造一套变体。包装是否会形成不同库存 SKU，仍需结合价格、采购单位和业务规则人工确认。

### 2. 误合并防线

- `钢筋扭矩扳手`、`钢筋保护套` 被标记为 `blocked`，不再因包含“钢筋”并入螺纹钢；
- `PPR内丝弯头` 与普通 `PPR弯头` 分开；
- PPR 的 `Φ110`、`DN110`、`110` 和 `110/50` 规格归一到同一规格表达；包装数量不会被当成管径；
- “螺丝”保留为泛称，词法候选只能进入人工复核，不自动改写为“螺钉”；
- 仅有相似文字的候选输出到 `fuzzy-review-candidates.jsonl`，决策固定为“人工复核，不自动合并”。

### 3. 单位是门禁证据，不是聚类条件

同一族出现 `件/套/米/吨` 等单位时，v0.2 不会隐藏它，也不会把数量直接相加，而是输出：

- `uom_quality.status`：`consistent`、`normalized_consistent_with_aliases`、`same_name_conflict`、`mixed_family_conflict` 或 `missing`；
- `quantity_by_uom`：分单位汇总；
- `review_status`：单位冲突时为“单位字段待复核”；
- `auto_ready_multi_attribute`：只有显式族、多个规格、单位无冲突且无阻断项时才为 `true`。

## 运行

```powershell
python scripts/material_master/discover_procurement_frequency_v0_2.py `
  --source "$HOME\Downloads\龙华项目物料待导入清单.xlsx"
```

输出目录默认为 `.runtime/material-master/frequency-discovery-v0.2/`，与 v0.1 并列保存，不覆盖首轮结果：

- `discovery-summary.json`：运行版本、覆盖率、门禁和质量统计；
- `source-rows.jsonl`：每条采购行的物料族候选、属性、规格键和单位；
- `clusters.jsonl`：物料族候选、频次、采购会话、变体、别名组、属性和阻断项；
- `fuzzy-review-candidates.jsonl`：相似候选对及人工复核原因。

所有输出都明确记录 `writes_erpnext: false`。

## 如何解释结果

- `integration_rank` 适合决定先审哪一族，综合采购事件、规格丰富度和别名证据；
- `frequency_rank` 适合找“实际反复发生”的物料族；
- `line_count` 保留原始采购行事实，不能直接当作采购次数；
- `distinct_event_count_approx` 是近似事件数，因源表没有采购单号，不能替代正式单据统计；
- `auto_ready_multi_attribute` 只是进入人工确认队列的门禁，不代表可以自动发布 SKU；
- `blocked`、`unresolved`、单位冲突和服务/笼统行必须先处理，不能靠文字相似度自动归类。

## 复核与下一步

第二轮已经扩大了候选覆盖，但也证明“候选发现”和“可发布物料”必须分开：词法候选占比高，单位冲突仍多，源表没有正式采购单号，且品牌、包装、供应范围可能影响价格或库存单位。下一步应在工作台中按以下顺序审阅：

1. 先看显式族的原始行、属性和 GPC 范围；
2. 再看 `multi_spec_candidate`，确认哪些属性真正造成价格/库存差异；
3. 对单位冲突、阻断项和词法候选逐项给出保留、拆分或合并决定；
4. 将已确认的族规则沉淀到规则目录，再处理后续第 101–300 行或完整 1,273 行；
5. 只有人工确认完成后，才进入多属性采购卡和 ERPNext SKU 映射，v0.2 本身不执行写入。
