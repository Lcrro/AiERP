# Material Catalog PostgreSQL Layer

This is the PostgreSQL-backed material catalog used by the Agent search layer.

It is separate from ERPNext. ERPNext remains the final business system and stores approved `Item` records. PostgreSQL stores the larger search/catalog layer: reviewed purchase names, aliases, draft standard items, manual review queues, and non-stock services.

## Why PostgreSQL

- The reviewed purchase catalog is already larger than a simple config file.
- Search needs aliases, typo handling, group filtering, audit fields, and later logs.
- PostgreSQL can support normal relational constraints now and better search later through indexes, `pg_trgm`, full-text search, or embeddings.
- It is closer to the future production architecture than CSV/SQLite.

## Tables

| Table | Purpose |
| --- | --- |
| `material_groups` | Group tree derived from paths such as `管件/镀锌管件`. |
| `material_group_mappings` | Mapping from reviewed group paths to canonical group paths. |
| `material_items` | Deduplicated standard item candidates from the review. |
| `material_aliases` | Raw names, slang, typos, and supplier names mapped to candidates. |
| `material_manual_review_queue` | Rows that must ask a human before creating or selecting an item. |
| `material_non_stock_services` | Freight, repairs, installation, and other service/expense rows. |

## Grouping Strategy

The first version keeps the full reviewed group path, then splits it into levels:

```text
管件/镀锌管件
  -> level1 = 管件
  -> level2 = 镀锌管件

安全消防/消防接头/铝合金
  -> level1 = 安全消防
  -> level2 = 消防接头
  -> level3 = 铝合金
```

This is intentional. We do not want to flatten all items into ERPNext's broad groups too early, and we do not want the LLM to invent a new taxonomy every time.

The governance rule is:

```text
reviewed group path
  -> PostgreSQL material_groups
  -> approved mapping to ERPNext Item Group
  -> final ERPNext Item
```

## Import

First export the reviewed CSV files:

```powershell
pwsh -ExecutionPolicy Bypass -File scripts/export_review_catalog.ps1
```

Then import them into PostgreSQL:

```powershell
$env:MATERIAL_CATALOG_DATABASE_URL="postgresql://user:password@localhost:5432/nexterp_agent"
python scripts/import_review_catalog_to_postgres.py
```

The import creates or updates:

- groups
- item candidates
- aliases
- manual review queue
- non-stock service rows

It is idempotent for the current review export: repeated runs update existing rows instead of duplicating them.

## Search Integration

Use `PostgresCatalogSearchClient` with the existing `MaterialSearch` scoring layer:

```python
from nexterp_agent.item_master import MaterialSearch, PostgresCatalogSearchClient

client = PostgresCatalogSearchClient("postgresql://user:password@localhost:5432/nexterp_agent")
search = MaterialSearch(client)
result = search.search_items("铜鼻子300A")
```

The client returns item-shaped rows with:

- `item_code`: temporary `REVIEW-MAT-*` code
- `item_name`: reviewed standard name
- `item_group`: reviewed group path
- `stock_uom`: unit
- `specification`: reviewed structured specs
- `alias_names`: raw purchase names and aliases

These temporary codes are for search and confirmation only. Final ERPNext item codes must still be generated by the coding engine.

## Classification Quality

The current groups are good enough for a first searchable catalog because they came from row-by-row review, not a blind automatic classifier.

They are not final ERPNext master data yet. Before automatic creation, the next governance pass should:

1. Merge duplicate group names that mean the same thing.
2. Split oversized groups such as broad tools or consumables when needed.
3. Add ERPNext Item Group mappings.
4. Mark safety-critical groups as manual-confirmation-required.
5. Add required spec templates per group.

The first PostgreSQL import currently creates `641` reviewed group paths. This is expected for the raw review stage, because similar concepts may still appear under different names, for example:

```text
劳保耗材/手套
劳保用品/手套
```

These should not be treated as permanent ERPNext groups. The next classification pass should create canonical group mappings while keeping the original reviewed paths for audit and alias learning.

`material_group_canonical_mapping.csv` is now imported into PostgreSQL as `material_group_mappings`, and each `material_items` row stores:

| Field | Meaning |
| --- | --- |
| `item_group_path` | Original reviewed group path. |
| `canonical_group_path` | Governed group path used by search results. |
| `canonical_level1` / `canonical_level2` / `canonical_level3` | Split canonical hierarchy. |
| `group_mapping_confidence` | Confidence from the group governance rule. |
| `group_mapping_reason` | Rule or override explanation. |
| `group_needs_human_review` | Whether the group requires manual review before automatic creation policy. |

Search results expose the canonical path as `item_group`, while preserving the original reviewed path in `data.reviewed_group_path`.

Example:

```text
reviewed_group_path = 劳保耗材/手套
canonical_group_path = 劳保用品/手部防护/手套
```

## Safety Rules

- Rows in `material_manual_review_queue` must not be auto-created.
- Rows in `material_non_stock_services` must not become stock items.
- Safety-critical groups need human confirmation before creation: 吊装索具、消防、安全绳、救生衣、压力仪表、危险化学品。
- PostgreSQL search can recommend candidates, but ERPNext creation still goes through `prepare_item_from_intent` and `create_item_from_intent`.
