## 一、项目背景

### 1.1 Nexterp 正在解决的不是普通“物料表”问题

Nexterp 的目标，是让施工项目的材料申请、审批、询价、采购、收货、库存和项目领退料使用同一套可追溯物料身份。员工看到的是易用的业务门户和商城式物料目录，ERPNext/Frappe 则继续作为无头事务内核，负责权限、工作流、正式单据、库存流水和审计事实。

这意味着物料目录必须同时满足三类要求：

- **用户能找到**：现场叫法、简称、俗称和历史名称能够召回正确物料；
- **采购能区分**：规格、材质、等级、接口、包装等会影响价格或适配的属性不能丢失；
- **ERP 能落账**：最终必须解析为唯一、稳定、已启用的数字 Item Code 和明确库存单位。

如果只是把历史 Excel 中的每一行原样导入 ERPNext，虽然导入速度快，但会把别名、错别字、重复规格、泛称和错误单位永久固化成主数据。后续采购、库存和项目成本都会围绕这些重复物料继续累积，清理成本远高于导入前治理。

### 1.2 当前系统已经具备的基础

目前物料体系已经完成了几块关键基础设施：

| 层次 | 当前作用 | 已有基础 | 尚缺能力 |
|---|---|---|---|
| GS1 GPC 2026-05 参考目录 | 提供官方分类边界和定义 | 官方四层目录可查询，内部扩展隐性标记 | GPC 只回答“属于什么类别”，不提供企业实际 SKU |
| Nexterp 参考目录数据库 | 保存内部标准类型、任意层级、属性和实际物料 | SQLite 目录可随数据库 revision 更新页面 | 历史采购名称尚未全量映射到稳定物料族 |
| 已确认物料目录 | 支撑商城选料和 ERPNext 业务 | 测试账套已有 259 个已确认并回读一致的数字 SKU | 覆盖面仍小于真实项目历史采购需求 |
| 物料采购商城 | 提供分类树、搜索、卡片和属性选择 | 螺栓等物料已经验证“一个族卡片选择具体规格”的体验 | 还缺系统化识别哪些物料应合并成族卡片 |
| ERPNext 测试账套 | 负责正式物料、单据、库存和工作流 | 259 个 Item、UOM、项目及采购业务链已经可回读 | 只能接收确认后的 SKU，不能替代源数据治理 |

因此，分类目录、采购页面和 ERPNext 内核都已经具备，当前缺口集中在中间一层：**怎样从真实采购记录中识别同一物料族、保留不同规格，并决定先治理哪些族。**

### 1.3 1,273 条实际采购清单反映的现实问题

龙华项目“实际采购清单”共有 1,273 条材料记录、991 个不同原始名称。它不是一张已经整理好的物料主数据表，而是现场采购历史的混合证据，包含：

- 同一物料的简称、全称、品牌前缀、现场俗称和不同符号写法；
- 同一物料族的不同口径、长度、材质、等级、接口和包装；
- “螺丝”“接头”“灭火器”等范围过宽、不能直接建料的泛称；
- 件、套、米、包、卷、吨等历史单位混用；
- 23 条服务或物流记录、1 条笼统批次记录以及少量数量异常；
- 缺少正式采购单号，只能通过日期、工序和规格近似还原采购事件；
- 价格、单位和规格字段完整程度不一致，不能直接横向比较。

1,273 是采购记录数，991 是原始名称数，它们都不等于应创建的 SKU 数。正确的处理方式是先识别物料族，再把会改变采购、库存或互换性的属性保留为不同 SKU。

### 1.4 用户界面已经把数据问题暴露出来

采购商城曾按“一个 SKU 一张卡片”展示钢筋、螺栓、接线端子和 PPR 管件。同一种物料只因规格不同就占据大量卡片，用户需要滚动很久才能找到目标；名称相似但结构不同的物料又可能排列在一起，增加误选风险。

螺栓等试点已经证明更合理的交互是：

```text
先看到一个明确标准类型
→ 打开规格选择器
→ 按业务顺序选择关键属性
→ 完整选择后解析到唯一 SKU
→ 再查询该 SKU 的价格和项目库存
```

但这种设计不能对所有名称机械套用。“PPR三通”适合有限属性选择器；“高压胶管”需要长度、结构和接口组成的配置型表单；“螺丝”则必须先拆成六角螺栓、内六角螺钉、自攻螺钉等明确类型。高频发现算法正是用来决定这三种情况各有哪些、先做哪些。

## 二、为什么目前急需开发

### 2.1 业务门户已经进入真实流程阶段，目录质量成为主阻塞

物料门户已经不只是分类演示。商城选料会继续进入材料申请、审批、询价、采购订单、收货和库存。门户只允许“本地已发布且 ERPNext 已启用”的物料进入申请，这是正确的安全边界，但也意味着目录覆盖不足会直接变成业务不可用：用户找不到物料、不得不临时绕过系统，或者要求重复新增。

如果先继续扩展页面，而不处理物料族和别名，系统会出现“页面看起来完整，但实际物料找不到或选不准”的情况。此时问题不在 UI，而在物料身份层。

### 2.2 继续逐条人工整理，投入会被低频长尾吞没

最新分析把 807 个候选族分成：19 个高频多规格、19 个高频单规格、39 个低频多规格和 730 个一次性/低频族。若按 Excel 顺序逐条整理，审核人员大部分时间会花在低频长尾上，而真正反复采购、最影响使用体验的物料可能很晚才被处理。

高频算法把工作顺序改成：

```text
先治理反复出现且规格丰富的物料族
→ 一次建立标准类型、属性和别名规则
→ 同时覆盖多条历史记录和后续新采购
→ 低频长尾保留证据、按需处理
```

这不是单纯提高统计效率，而是在有限审核人力下显著提高每一次人工确认的覆盖收益。

### 2.3 重复物料一旦进入 ERPNext，修复成本会快速上升

同一物料以多个 Item Code 入账后，库存余额、历史价格、供应商报价、采购订单和项目用量会被分散。之后即使发现它们实际相同，也不能简单删除或改号，因为已经产生审计记录和库存流水。

现在仍处于独立测试账套和受控发布阶段，是治理成本最低的窗口。先冻结族边界、必选属性、单位策略和别名，再发布 SKU，可以避免未来在有正式库存和单据后做高风险主数据合并。

### 2.4 多规格商城体验依赖物料族，不能靠前端临时拼组

商城中把多个 SKU 合并成一张卡片，必须有稳定的标准类型和属性模型。若仅在前端按名称前缀临时分组，会产生三类严重问题：

- 把普通弯头和内丝弯头、灭火器和灭火器箱等不同物料误合并；
- 漏掉品牌前缀、错别字或简称不同但实际同族的 SKU；
- 用户选完属性后不能唯一解析 Item Code，导致申请和库存查询失败。

因此，多规格整合首先是主数据与算法问题，其次才是页面展示问题。

### 2.5 单位和价格治理必须在频次统计阶段同步完成

历史表存在同族多单位现象。如果只按名称合并并直接累加数量，会得到没有业务意义的总数；如果直接比较单价，还可能把“每米”“每件”“每包”的价格放在一起。高频发现链路已经把数量按单位分开，并把单位策略作为发布门禁。

尽早开发这层能力，可以阻止错误单位继续进入询价、采购和库存；拖到交易发生后再修，会同时影响数量、价格、库存余额和项目成本。

### 2.6 需要尽快建立可复用规则，而不是不断做一次性代码修改

过去每发现一组螺栓、接头或端子，就单独修改数据或页面，能够解决眼前问题，但难以覆盖下一批清单。高频发现的目标是把经验沉淀为版本化资产：

- 已审核别名；
- 标准类型中心词与禁止合并边界；
- 规格和单位解析规则；
- 选择器/配置型模板；
- 完整来源身份和审核记录。

规则冻结后，新采购清单可以重复运行并复用已有决策，只有新别名、新规格和冲突项需要增量审核。这才可能从 1,273 条扩展到未来更多项目，而不让维护工作量与行数同比增长。

### 2.7 现在必须先建立金标准，避免把错误自动化

当前词法和向量评测仍表明标准化证据不足。若在人工金标准尚未建立时启用模糊合并、向量自动选择或学习排序，错误别名会反过来污染目录，形成“系统因为历史错误而更确信错误”的闭环。

所以当前急需开发的不是更激进的自动化，而是一个可审计的高频候选、人工审核、规则冻结和回归评测闭环。它既能提高近期整理效率，也为将来是否值得使用向量召回或学习排序提供可靠判断基础。

### 2.8 如果现在不做，最直接的后果

短期会表现为商城卡片过多、搜索结果不稳定、用户选错或找不到物料；中期会表现为重复建料、单位不一致、价格不可比和库存分散；长期则会使项目成本分析、供应商比价、补货预测和跨项目复用都建立在不可靠的物料身份上。

从项目节奏看，GPC 目录、参考数据库、ERPNext 测试账套、采购门户和多规格交互都已具备，当前正好到了必须补齐“真实采购记录 → 标准物料族 → 唯一 SKU”中间链路的阶段。继续绕过这层开发，其他业务页面的边际收益会迅速下降。

## 三、项目目标

本项目要从 1,273 条实际采购记录中找出出现最频繁、最值得优先标准化的物料。统计对象不是原始名称，也不是具体 SKU，而是“标准物料族”：

- 同一种物料的简称、别名、品牌前缀和常见写法可以归到同一物料族；
- 同一物料族的不同规格可以合并统计族级频次，但每个规格仍保留为独立 SKU；
- 结构、用途或安全属性不同的物料不得因为名称相似而强行合并；
- 频次只决定复核和多属性整合的优先级，不直接产生物料主数据。

例如，`PPR弯头`、带品牌前缀的 PPR 弯头和不同口径/角度的 PPR 弯头，可以在“PPR弯头”族中统一统计；但 `PPR内丝弯头` 不能仅因文字相似而自动并入普通 PPR 弯头。选定口径、角度、接口等必选属性后，仍必须对应唯一 SKU。

## 四、当前结论

目前已经具备可重复运行、可审计、不会写入 ERPNext 的高频物料发现链路。最新 v0.6 结果如下：

| 指标 | 当前结果 | 解释 |
|---|---:|---|
| 实际采购记录 | 1,273 行 | 原始非空材料行 |
| 不同原始名称 | 991 个 | 未做别名归并前的名称数 |
| 物料族候选 | 807 个 | v0.6 的族级审核对象 |
| 有族假设的行覆盖率 | 99.61% | 仅表示已有候选，不代表归类正确率 |
| 高频多规格族 | 19 个 | 最适合优先做多属性整合 |
| 高频单规格族 | 19 个 | 高频但暂未发现足够规格变化 |
| 低频多规格族 | 39 个 | 有整合价值，但优先级低于高频族 |
| 一次性或低频候选族 | 730 个 | 尚未完成跨族别名/规格归并审计，不能视为 730 个已确认独立物料族 |
| 族模板可进入人工审阅 | 35 个 | 模板字段结构可审，不等于可发布 |
| 发布准备可进入人工审阅 | 2 个 | 同时通过部分单位和源证据门禁 |
| 已定义单位策略 | 16 个族 | 791 个族仍缺正式单位策略 |
| 阻断族 | 27 个 | 服务、笼统采购、数量异常或特定物料 |
| 有价格的采购行 | 1,103 行 | 只有单位可信时才允许比较价格 |
| 模糊相似候选 | 4,902 对 | 当前全部为人工复核/禁止自动合并 |
| ERPNext 写入 | 0 | 所有轮次均为只读分析 |

v0.6 对 21 个高优先族进一步给出了页面形态建议：

- `selector`：14 个，适合在同一标准类型下选择有限属性；
- `configurable`：4 个，需要补齐较完整配置后才能确定物料；
- `split_required`：3 个，族名过宽，必须先拆成明确标准类型；
- 其中只有 `PPR三通` 当前达到 `ready_for_template_review`，其余仍需处理属性、单位或族边界。

因此，本项目已经解决“先从哪里下手”的问题，但尚未完成“全部自动归并并直接发布”的问题。当前正确的交付定位是：**高频物料发现与人工审核决策系统**，不是自动建料系统。

## 五、算法口径

### 5.1 总体流程

```text
Excel 原始行
→ 完整来源身份与内容哈希
→ 名称、单位、数字和符号规范化
→ 显式标准类型规则
→ 标准类型中心词与词法候选
→ 族级属性解析和规格键
→ 按物料族聚合别名与规格变体
→ 计算频次、变体、单位和价格证据
→ 生成审核队列
→ 对齐现有目录，给出 selector/configurable/split 决策
```

显式规则优先处理边界较清楚的施工物料，例如 PPR 管件、螺栓、钢筋、高压胶管、灭火器、接线端子等。无法可靠识别的名称不会因文本相似而静默合并，而是保持独立或进入词法复核队列。

### 5.2 物料族、别名和规格的关系

算法把四个概念分开保存：

- `raw_name_count`：原始表中不同叫法的数量；
- `alias_candidate_group_count`：相同规格键下疑似为别名的名称组；
- `variant_count`：同一物料族内不同技术规格键的数量；
- `line_count` / `deduped_event_count`：原始行频次和去重后的近似采购事件。

同族不同规格只在族级统计时合并，具体物料编码不合并。品牌和包装通常保留为证据或采购条件，不默认制造新规格；当包装会影响库存单位、价格或交付形态时，必须人工决定是否拆 SKU。

### 5.3 频次指标

当前同时保留多种指标，避免把一个数误称为“真实采购次数”：

- `line_count`：原始行出现次数；
- `active_purchase_date_count`：出现过采购的日期数；
- `purchase_session_count`：日期与工序组成的近似采购会话数；
- `deduped_event_count`：按日期、工序和技术规格键去重的近似事件数；
- `variant_count`：同族技术规格数量；
- `quantity_by_uom`：按单位分别汇总，禁止把件、米、吨直接相加；
- `market_value_sum`：数量、单位和单价可用时的金额证据。

源表没有正式采购单号，因此任何一个指标都不能替代 ERPNext 采购单据中的真实订单次数。

首轮的透明整合优先分数为：

```text
ln(1 + 原始行数)
× [1 + ln(1 + 规格数 - 1)]
× [1 + 0.25 × ln(1 + 别名数 - 1)]
```

该分数只用于安排审核先后。v0.6 最终是否建立多属性选择器，还要同时看目录边界、必选属性、单位证据和人工决策。

### 5.4 来源身份与审计

每条来源记录现在使用完整组合身份：

```text
source_dataset + source_document + source_sheet + source_row
```

同时保存稳定字段生成的 `source_row_hash`。相同行号出现在不同数据集、文件或工作表时不会再被误关联；同一组合身份的源内容发生变化时，哈希冲突会阻止旧结论继续沿用。

## 七、当前高优先物料族

## 八、已解决的问题

1. 不再把原始名称出现次数直接当成物料频次；已支持族级统计。
2. 别名、规格变体、品牌、包装和采购事件已分开保存。
3. 未知物料不再因为文字相似被静默归并。
4. 已阻止典型误合并，例如钢筋工具并入钢筋、普通弯头并入内丝弯头、灭火器并入灭火器箱。
5. 高压胶管、PPR、灭火器和垫圈已采用族级属性解析，避免通用规格正则误读。
6. 历史单位和推荐单位已分开；单位冲突时数量不直接相加，价格不直接比较。
7. 审核队列已经互斥并覆盖 807 个族，不再遗漏低频多规格族。
8. 来源身份已由裸 `source_row` 升级为完整命名空间和内容哈希。
9. 所有模糊/向量结果只作为候选，不参与自动选料和 ERPNext 写入。

## 九、当前问题与风险

### 9.1 候选覆盖率不是准确率

99.61% 的行已经有族假设，但其中 1,050 行仍来自词法候选，另有 23 行为混合规则置信度。它说明系统很少“完全没猜测”，不说明猜测已经正确。

### 9.2 缺少正式采购单号

源表只能通过日期、工序和规格近似去重。同一天的重复行可能是重复导出，也可能是真实分批采购。报告中的近似事件不能用于财务或供应商绩效统计。

### 9.3 单位策略是最大阻塞项

807 个族中只有 16 个定义了单位策略，791 个仍待定义。历史表中的件、套、米、包、卷等经常混用；任何自动换算都可能放大数量和价格错误。

### 9.4 泛称必须先拆分

`螺丝`、`膨胀螺丝`、`灭火器` 等高频词不是足够精确的标准类型。若直接做一个大选择器，会把结构和安全属性不同的物料混在一起。

### 9.5 人工金标准尚未形成

当前已建立 300 条正样本候选和 100 条困难负样本候选，但正式人工确认计数仍为 0/0。19 条高风险记录已做模型辅助复核，只能作为银标/评测证据，不能冒充真人金标准或自动晋级生产别名。

### 9.6 向量和学习排序暂不适合进入生产

当前 49 条目录链接银标样本的词法 Top-1 为 44.90%，Recall@5 为 57.14%；本地向量影子通道没有提高这两项指标，且增加了延迟。生产检索顺序保持：

```text
数字编码精确匹配
→ 已审核别名
→ 标准类型中心词
→ 规格/单位精确解析
→ 词法候选
→ 向量仅作离线候选补充
```

自动选择只允许“唯一数字编码”，或“已审核别名 + 所有必选属性完全一致”。向量分数无论多高都不能自动确定物料。

### 9.7 730 个一次性或低频候选族并未证明彼此独立

`one_off_or_low_repeat` 是聚类完成后的频次象限，不是业务审核结论。当前算法为了防止误合并，只对显式且边界清楚的类型执行跨规格聚合；未识别的名称即使可能互为别名、同族不同规格，也会先保持为两个低频候选。因此 730 是保守拆分后的候选上限，最终确认的独立物料族数量大概率会更少。

对当前 730 个候选族的二次审计结果为：

- 共覆盖 873 条来源行；
- 712 个仍是词法候选，只有 12 个来自显式族规则；
- 728 个尚未定义族级单位策略；
- 9 个族内部已经出现疑似别名组；
- 604 个候选族至少参与一组模糊相似关系；
- 其中 352 个候选族参与语义近似关系，共 674 对；
- 涉及低频候选的相似关系共 4,854 对，其中 4,180 对带结构/规格差异信号；
- 78 对被列为当前优先语义复核对象。

这些关系不能直接等同于重复物料。例如：

- `盾构铜塔接头 / 盾构铜比塔接头`、`注塞泵75kW / 柱塞泵75kW` 很可能是错别字或同一物料别名；
- 不同规格的 O 型圈、高压接头或黄油咀可能应归入同一标准类型，但仍是不同 SKU；
- `美工刀 / 美工刀片`、`钢丝绳 / 钢丝绳扣` 名称接近，却不是同一物料，也不应合并成同一 SKU。

因此，不能因为它们当前频次低就永久暂缓。必须先做一次跨族归并审计，把结果分成“同一 SKU 的别名”“同族不同 SKU”“不同物料”和“证据不足”四类，然后重新计算族级频次。经确认的低频候选合并后，部分物料族可能上升为高频或多规格优先族。

## 十、下一阶段建议

### 基础校准：低频候选族二次归并审计

在把 730 个候选全部放入低优先级长尾前，应先执行一轮分层审计：

1. 先审核 78 对优先语义候选，处理明显错别字、品牌前缀和词序差异；
2. 再审核其余语义近似关系，并用标准类型中心词、规格、单位和现有数字 SKU 约束；
3. 对结构敏感关系只判断“是否同族”，不得直接合并 SKU；
4. 明确区分四种结论：同一 SKU 别名、同族不同规格、不同物料、证据不足；
5. 冻结审核结论后重新聚类和计算频次，再确定真正的高频与长尾队列；
6. 全过程保留完整来源身份和内容哈希，不写 ERPNext，不把模糊分数当作自动决定。

### 第一优先级：审核 21 个高频族

1. 先处理 3 个 `split_required`：螺丝、膨胀螺丝、灭火器；
2. 以 PPR三通为第一个属性选择器试点；
3. 依次审 PPR弯头、PPR截止阀、PPR直接、PPR管和铝合金快速接头；
4. 高压胶管、吊带、钢丝绳、无缝管采用配置型字段，不做简单规格按钮堆叠；
5. 每个族冻结标准类型、必选属性、描述属性、采购条件、单位策略和禁止合并边界。

### 第二优先级：完成人工审核数据集

1. 逐条确认 300 条正样本和 100 条困难负样本；
2. 正样本覆盖高频物料、别名、规格变体、品牌词和错别字；
3. 负样本覆盖易混淆类型、结构冲突和目录中不存在的物料；
4. 只有来源身份完整、`source_row_hash` 一致、审核人和时间完整的记录才可晋级已审核别名。

### 第三优先级：接入物料工作台

为每个候选族提供一张审核卡：

```text
族级频次与近似事件
→ 原始名称和来源行
→ 已解析规格/属性
→ 历史单位与冲突
→ 目录现有标准类型
→ 合并 / 拆分 / 保持独立
→ 冻结属性选择器或配置模板
```

审核通过后，物料采购页面才把同族多 SKU 聚合为一张卡片；用户完整选择必选属性后，再解析到唯一数字物料编码。

### 第四优先级：重新评估向量通道

只有同时满足以下条件才考虑继续维护向量召回：

- 人工确认正样本不少于 300 条；
- 困难负样本不少于 100 条；
- Recall@5 不低于 95%；
- Top-1 不低于 85%；
- 困难负样本误匹配率低于 1%；
- 相比词法 Recall@5 至少提高 5 个百分点；
- Top-1 不下降，并满足页面延迟要求。

达不到门槛时，继续使用确定性规则和人工审核，不为“技术先进”而维护无实际收益的向量通道。

## 十一、阶段验收标准

本阶段完成需满足：

- 同一来源文件和哈希重复运行，1,273 行输入及队列统计稳定；
- 不同数据源相同行号永远不能关联；源内容变化可以被哈希检测；
- 高频族的别名和规格可以聚合统计，但不同 SKU 不被合并；
- 所有 `split_required` 族完成拆分决策；
- 21 个高优先族均完成业务复核和单位策略；
- 300 条正样本、100 条困难负样本完成真人审核；
- 模糊和向量候选不能绕过属性、单位和人工门禁；
- 任何分析、评测和审核动作均不写入 ERPNext；
- 只有冻结并确认的标准类型、属性模板和别名才能进入后续受控发布流程。
